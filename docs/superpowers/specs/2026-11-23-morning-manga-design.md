# 朝ブリーフィング 8コマ漫画 設計書

作成: 2026-11-23（ユーザーとの対話と試し描きの結果から）

## 1. 目的と背景

- 毎朝の【デイトレブリーフィング】メールの下部に、8コマ漫画と文章の解説を入れる。
  題材は前営業日の経済ニュース・相場の動き・株用語・話題の銘柄、または当日の note 記事のひとつ。
- 狙い：相場の知識を、キャラクターの掛け合いで楽しく覚えてもらうこと。
- 分担：台本・画像生成プロンプト・画像のチェック・仕上げは Claude が行う。
  画像そのものは Codex（gpt-image-2）が描く。Claude は画像生成が得意ではなく、トークンも節約したいため。
- 作るのは**前日の夕方〜夜**。朝のブリーフィングは、できあがったものを**呼び出して貼るだけ**にする。
  6:40 の配信を遅らせないことと、朝の作業に別の仕事を混ぜてAIの注意を散らさないことが理由（ユーザー判断）。

## 2. ゴール／ゴールでないもの／失敗とみなすもの

**ゴール**
- 平日の朝メールに、横2コマ×4段の8コマ漫画（画像4枚）と解説文が毎日載る。
- キャラクターの見た目が毎回ほぼ同じ。
- セリフが読める（スマホ幅 390px でも読める）。

**ゴールでないもの**
- 漫画を note や X に流用すること（今回は朝メール専用）。
- 毎日違う画風に挑戦すること。

**失敗とみなすもの（動いていても失敗）**
- 漫画が原因で朝メールが遅れる、または送られない。
- 投資助言に当たる表現（売買の推奨・目標株価など）が漫画や解説に入る。
- 実在の銘柄を名指しで悪く描く。
- 確認していない数字を載せる。
- 文字化けした文字や、画像生成AIが勝手に描いた文字がそのまま載る。

| 人物 | 役割 | 見た目（設定画どおり） |
|---|---|---|

| ミライ | 新人トレーダー（女性）。知識が少なく、素直に質問する。読者の代わり | 栗色のボブ、黄色のヘアクリップ、紺ブレザー、白ブラウス、グレーのスカート、社員証、タブレット。可愛い雰囲気 |

## 4. 回の種類と台本のルール

### 4.1 回の種類

| 種類 | 内容 | 主な登場人物 |
|---|---|---|
| 相場の振り返り | 前営業日の指数・為替・セクターの大きな動きを1つ取り上げ、理由の手がかりを教える | 先生＋ミライ |
| 用語 | 株用語（例：SOX指数、連れ安、PTS、信用買い残）を1〜2個 | 先生＋ミライ |
| 話題の銘柄・テーマ | 当日の note 記事や、その日に話題の銘柄・テーマ | 先生＋ミライ（＋ゴンダ） |
| 注意喚起 | 高値掴み・イナゴ買い・ニュースへの飛びつきなどの失敗パターン | ゴンダ先輩が主役。先生が諭し、ミライが学ぶ |

- 注意喚起の回は**週2回まで**（Claude の判断。毎日だと説教くさくなるため）。
  ゴンダ先輩は、ほかの回にも脇役として出てよい。

### 4.2 台本のルール

- 8コマ。起（1〜2）・承（3〜5）・転（6〜7）・結（8）を目安にする。
- 吹き出しは1コマに1つ（掛け合いのコマでも最大2つ）。**1つの吹き出しは3行・1行12字まで**。
  スマホで読めるようにするため。2行以内が理想。
- **ゴンダ先輩の失敗には、銘柄名を出さない。**
  「SNSで話題の生成AI関連の小型株」「決算翌日にストップ高した電線株」など、状況から銘柄がおおよそ分かる程度にぼかす（ユーザー判断）。
- 投資助言に当たる表現を使わない（`docs/note-pipeline/editorial-rules.md` §1 と同じ）。
  ゴンダ先輩が「買いだ！」と言うのは失敗の描写としてよい。ただし、必ず同じ回の中で先生が考え方を正し、正しい形で終わらせる。
- 数字は、その日の JSON（`macro_result_closing.json` など）か、出典を確認できたものだけを使う。
  急落・急騰の原因は、裏付けがある場合だけ書く。
- note 記事を題材にする場合も、記事本文は書き写さない。要点を漫画用に言い直す。

### 4.3 解説文

- 漫画の下に 200〜350 字。
- 構成：用語の定義 → その日の数字 → 読者が明日から見られるポイント。
- 末尾に「※投資判断はご自身で。」を入れる。

## 5. 作り方の案（比較）

| 案 | 流れ | 長所 | 短所 |
|---|---|---|---|
| **A. GitHub Actions＋ChatGPT のログイン情報（採用）** | Claude が依頼を出す → Actions 上の Codex CLI が描く → Claude が確認・仕上げ | PC 不要で全自動。ChatGPT の有料プランの範囲で済む | ログイン情報（`auth.json`）の更新が途切れると、PC で再ログインして登録し直す必要がある。OpenAI は CI では API キーを推奨しており、この方法は「上級者向け」の扱い |
| B. 手元の PC の Codex で描く | 描く部分だけ PC で夜に自動実行 | 公式どおりの使い方で、ログインが安定 | 夜に PC が起動している必要がある |
| C. OpenAI の API キー | 案A のログイン情報を API キーに替える | 最も安定 | ChatGPT とは別に従量課金 |

- 採用理由：ユーザーは ChatGPT の有料プランのみを持っていて、PC に依存しない全自動を希望している。
  品質はどの案でも同じ（同じ gpt-image-2 を使う）。
- 案A で、ログインの切れが多い場合は案C に切り替える（Actions のログイン部分だけを差し替えられる作りにしておく）。
- 公式プラグインの `openai/codex-plugin-cc` と、有志の `codex-image-in-cc` はどちらも人が操作する前提のもの。
  自動実行では使わない（試し描きでは後者を使った）。

## 6. 全体の流れ（平日）

```
17:45  夕方の漫画タスク（Claude の定期タスク・新しいセッション）
        ├ 題材決め・台本・プロンプト・解説文を作る
        ├ GitHub Actions「manga_render」を起動（8コマ分の場面プロンプトを渡す）
        │     └ Codex CLI が参考画像つきで8枚を描き、ブランチ manga に置く（約10〜20分）
        ├ 8枚を確認 → ダメなコマだけ描き直しを依頼（最大2回）
        ├ 吹き出し・セリフを載せて横2コマ×4段の画像4枚に組む → 目で確認
        └ 非公開の納品先（Artifact）に、画像4枚＋解説＋manifest を置く
翌6:40 朝ブリーフィング（既存の定期タスク）
        └ 納品先から画像と解説を読み、メールの下部に貼る（無ければ漫画欄を省く）
```

- 金曜夕方に作った分は、月曜朝のメールに載せる。祝日の前日も同じ扱いで、次の営業日の朝に使う。
- 夕方の漫画タスクは、note の日次タスク（16:15〜17:28 納品）の後に動く。
  note の納品ページを題材の候補として読めるようにするため。
- 夕方の漫画タスクが**19:30 までに**終わらなかった場合、その日は漫画なしとする。
  ユーザーへの通知は「🐾 漫画は本日見送り：<理由>」。

## 7. 各部の設計

### 7.1 置き場所と公開範囲

このリポジトリは**公開**。台本・セリフ・解説文はリポジトリに置かない（編集ルールと同じ考え方）。

| もの | 置き場所 | 公開範囲 |
|---|---|---|
| 設定画（3人分） | `assets/manga/`（main） | 公開（ロゴと同じ扱い） |
| 生成プログラム・ワークフロー・プロンプト雛形 | `manga_pipeline/`、`.github/workflows/manga_render.yml`、`docs/manga/` | 公開 |
| 場面プロンプト（英語）と、文字なしのコマ画像 | Actions への入力、ブランチ `manga`（毎回1コミットに上書き。charts と同じ方式） | 公開。セリフを含まないので可 |
| セリフ・解説・完成画像（4枚） | 非公開の Artifact「朝マンガ納品」（固定 URL） | ユーザーのみ |

- 完成画像を Artifact に置くと、ユーザーが夜のうちに出来ばえを見られる利点もある。
- 漫画を作るのは毎回新しいセッションなので、作業ファイルは `WORK/`（gitignore 対象）に置く。

### 7.2 GitHub Actions：`manga_render.yml`

- **起動：** `workflow_dispatch` のみ。入力は `request`（JSON 文字列）。
  Claude は GitHub MCP の `actions_run_trigger` で起動する。
  `pull_request` などの外部から起動できるトリガーは付けない（秘密情報を守るため）。
- **request の中身：**
  ```json
  {"date":"2026-11-24","run_id":"r1",
   "panels":[{"n":1,"prompt":"<場面プロンプト>","refs":["mirai"]}, ...]}
  ```
  - 描き直しのときは、描き直すコマだけを入れる。
  - `refs` は参考画像のキー（`corgi` / `mirai` / `gonda`）。そのコマに出る人物の設定画だけを渡す。
- **手順：**
  1. Node を入れ、Codex CLI をバージョン固定で入れる。
  2. 秘密情報 `CODEX_AUTH_JSON`（base64）を `~/.codex/auth.json` に書き出す。
  3. コマごとに `codex exec` で画像生成機能を使い、参考画像を添えて描かせる。
     各プロンプトの頭には共通文（§7.3）を付ける。
  4. 画像を `panels/p{n}.png`（1024×1024）に保存する。
  5. ブランチ `manga` を、前回分の上に今回分を重ねる形で上書きする。
     置くのは `manga/<date>/p{n}.png` と、`manga/<date>/status.json`（コマごとの成否・生成時刻・run_id）。
  6. **ログイン情報の保存し直し：** 実行後の `~/.codex/auth.json` が変わっていたら、
     `gh secret set CODEX_AUTH_JSON` で秘密情報を更新する。
     これには、秘密情報の書き込み権限だけを持つ fine-grained PAT（秘密情報 `SECRETS_PAT`）を使う。
     OpenAI の CI/CD ガイドにある「Codex に更新させ、更新後の auth.json を保存する」方式に従う。
     自前で更新 API を呼ぶことはしない。
  7. ログに `auth.json` の中身やトークンを出さない（`::add-mask::` を使い、`set -x` は使わない）。
- **同時実行：** `concurrency: manga-render`（キャンセルせず待つ）。auth.json は同時に1か所でしか使えないため。
- **ログインが切れた場合：** ジョブを失敗させ、`status.json` に `"auth":"expired"` を書く。
  夕方の漫画タスクはこれを見て、通知に「Codex の再ログインが必要」と書く。
  ユーザーは PC で `codex login` → `base64 ~/.codex/auth.json` → GitHub の Secrets に登録し直す
  （手順は `docs/manga/README.md` に書く）。
- **未確認の点（実装の最初に確かめる）：** `codex exec` で画像生成を使うときのオプション名（参考画像の渡し方・機能フラグ・出力先）は、
  Codex CLI のバージョンで変わる。試し描きでは PC の Codex CLI 0.171.0 で動いた。
  Actions でも同じバージョンに固定し、`codex exec --help` で確かめてから書く。

### 7.3 場面プロンプト（Claude が作る）

共通文（`docs/manga/prompt-common.md` に置き、Actions が各コマの頭に付ける）:

```
Use the attached character sheets as references; keep faces, outfits and colors identical.
Single manga panel, Japanese manga style, clean line art with soft cel shading, bright colors, 1024x1024.
Leave the top 30% of the panel as simple background for speech bubbles added later.
Do NOT draw any text, letters, numbers, speech bubbles or logos (charts may use simple shapes only).
Scene:
```

- 場面は英語で、1コマ2〜3文。人物の位置（左／右）を必ず書く。吹き出しの尻尾の向きに使うため。
- 下落の話ならグラフは下向き、のように絵と内容を一致させる。試し描きでは3コマ目のグラフが上向きになった。

### 7.4 Claude の確認（コマごと）

8枚を見て、次のどれかに当たるコマは描き直しを依頼する。

1. 文字・数字・吹き出し・ロゴが描かれている
2. 人物の顔・服・色が設定画と明らかに違う（コーギー先生の目が笑い目でない、ミライのヘアクリップが無い、など）
3. 場面の内容と絵が合っていない（例：下落の話なのにグラフが上向き）
4. 上の3割に吹き出しを置く余白が無い、または人物が小さすぎる
5. 手指・体の破綻が目立つ

- 描き直しは最大2回、1回あたり最大8コマ（ユーザーは ChatGPT Plus。1日の生成は最大24枚。ユーザー判断で「まずこれで試す」）。2回目でもダメなコマは、軽い問題（5）なら採用する。
  重い問題（1〜3）が残る場合は、その日の漫画を見送る。
- 描き直しでは、場面プロンプトに直す点を足す（例：「the chart line goes DOWN」）。

### 7.5 仕上げ：`manga_pipeline/compose.py`

試し描きの見本（2026-11-23）と同じ仕上がりにする。

- 入力：コマ画像8枚と `script.json`（コマごとの話者・セリフ・吹き出しの位置）。
- 出力：`row1.jpg`〜`row4.jpg`（各 1360×684px、横2コマ。1コマ 660px。JPEG 品質85、各200KB以内）。
- 吹き出し：白の角丸、黒枠3px、尻尾は話者の方向へ。
  文字は Noto Sans JP Bold 34px（`note_pipeline/fonts.py` の静的フォントを使う）。
  吹き出しの位置は `script.json` の `x`（0〜1）で指定する。
- 枠：黒4px。右下に紺丸（直径34px、#1E3A5F）で白抜きのコマ番号（1〜8、22px）。
- 見本の数値（試し描きの組版で使った値。これに合わせる）：段の画像は余白12px・コマ間16px。
  吹き出しは上端から14px、内側の余白は左右24px・上下18〜20px、角の丸み28px、行間8px。
  尻尾は吹き出しの下端から34px下の、話者の x 位置へ向ける。吹き出しの横位置は話者の x を中心に、コマ端から14px以上離す。
- フォントについて：ユーザーの「Meiryo UI」指定は Word・Excel などの出力物向け。
  画像は Linux で描くので Noto Sans JP を使う（Claude の判断）。
- Claude は組み上がった4枚を目で見て、吹き出しが顔に重なっていれば `x` を直して組み直す。
- テスト：吹き出しの折り返し（1行12字・3行まで、超えたらエラー）、出力サイズ、ファイルサイズ。

### 7.6 納品（Artifact「朝マンガ納品」）

- 固定 URL の非公開 Artifact。index.html は、その日の漫画と解説を表示するページ（ユーザーの確認用）。
- `files`:
  - `manga/row1.jpg`〜`row4.jpg`
  - `manga/manifest.json`：
    ```json
    {"for_date":"2026-11-24","made_at":"2026-11-23T18:40+09:00","title":"SOX指数と連れ安",
     "rows":[{"file":"row1.jpg","sha256":"…"}, …],
     "explanation_html":"<p>…</p><p>※投資判断はご自身で。</p>"}
    ```
- `for_date` は、漫画を載せる朝の日付（次の営業日）。

### 7.7 朝ブリーフィング側の変更

既存の朝ブリーフィングの定期タスクのプロンプト（リポジトリ外）に、手順を1つ足す。
朝ブリーフィングも夕方の漫画タスクも、同じアカウントの Claude の定期タスク（クラウド）。
そのため、Artifact の読み書きは同じ持ち主どうしで行える。
プロンプトの書き換えと新しい定期タスクの作成は Claude が行う（ユーザーの承認を得てから）。
手順の本文は `docs/manga/briefing-manga.md` に置き、プロンプトからはそれを参照する（チャートの `docs/briefing-charts.md` と同じ方式）。

1. Artifact「朝マンガ納品」の `manga/manifest.json` を `action: read, path` で読む。
   `for_date` が今日でなければ、漫画欄を丸ごと省く（注記もしない）。
2. `row1〜4.jpg` を読み、sha256 を確かめる。
3. メールの最下部（チャートと本文の後、フッターの前）に次を置く。
   - 見出し「🐾 コーギー先生の8コマ相場教室「<title>」」
   - 画像4枚：`<img src="cid:attN" width="100%" style="max-width:680px;height:auto;display:block;margin:4px 0">`
   - 「📝 解説」と `explanation_html`
4. 添付はチャートの後ろに続けて並べる（`inline: true`）。
5. 漫画の添付で下書き作成に失敗したら、漫画を外して作り直して送る。チャートより先に漫画を外す。

## 8. 実装前の準備（ユーザーと Claude）

- **最初の作業は、無人で描けるかの確認とする。** Actions 上の `codex exec` で、参考画像つきの1コマを描かせる。
  描けなかったら、そこで作業を止めてユーザーに相談する（案B／案Cの選択。ユーザー判断）。
  描けた場合も、ログイン情報の書き戻しが1往復成功することを確かめてから、先へ進む。
0. 設定画は、ユーザーが PC の Codex で描く（試し描きと同じ方法）。Claude はプロンプトを用意し、受け取った画像をリポジトリに置く。
1. **ゴンダ先輩の設定画の描き直し**（試し描きの版は目が細い釣り目になっていなかった）。
   - デフォルメを強める。
   - 細い釣り目にする。
   - 3人の並び図も作り直す。身長はそろえてよい。
   - 決まった3枚を `assets/manga/corgi_sensei_sheet.png`・`mirai_sheet.png`・`gonda_sheet.png` に置く。
2. **ログイン情報の登録（ユーザー作業）：**
   - PC で `base64` した `~/.codex/auth.json` を、リポジトリの Secrets `CODEX_AUTH_JSON` に登録する。
   - 秘密情報の書き込みだけを許可した fine-grained PAT を作り、`SECRETS_PAT` に登録する。
   - 手順書は Claude が `docs/manga/README.md` に書く。
     ユーザーは PAT の作り方を知らないため、GitHub の画面のどこを押すかまで、1手ずつ書く。
     PAT の作成と Secrets の登録は、ユーザーの GitHub ログインでしかできない。Claude には代行できない。
   - Actions に登録した後は、**同じ auth.json を PC 側で使い続けない**。PC で再ログインして、別のログイン状態にしておく
     （同じログイン情報を2か所で使うと、更新が衝突するため）。
3. 夕方の漫画タスク用の定期タスクを作り、朝ブリーフィングの定期タスクのプロンプトを更新する。
