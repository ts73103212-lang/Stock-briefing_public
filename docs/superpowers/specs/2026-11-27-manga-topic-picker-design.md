# 朝マンガ ネタ選び 設計書

作成: 2026-11-27（ユーザーとの対話から）
前提: `docs/superpowers/specs/2026-11-23-morning-manga-design.md`（以下「元の設計書」）の仕組みが稼働中。1週間、漫画の質・内容・メール配信とも問題なし（ユーザー評価）。

## 1. 目的と背景

- いまは夕方の制作タスクが、ネタ選びから漫画の完成までを一貫して行っている。
- これを、note のネタ選び（ネタ選びページで候補を見て、ユーザーが選んだものを書く）と同じ運用にする。
  ユーザーが読みたいネタ・伝えたいネタを選べるようにして、漫画の魅力を上げるため。
- ユーザーが選ばなかった日は、これまでどおり Claude が選んだネタで描く（毎朝の配信は止めない）。

## 2. ゴール／ゴールでないもの／失敗とみなすもの

**ゴール**
- 平日 14:00 ごろ、ネタ候補 **4件＋自由記述欄** が、専用のネタ選びページに出る。各候補に難易度 ☆1〜3 が付く。
- ユーザーが **20:00 まで** に1件を選ぶか、自由記述で頼むと、その晩の制作がそのネタで漫画を描く。
- 選択がない日は、Claude が選んだネタで描く（いまと同じ）。

**ゴールでないもの**
- note のネタ選びページ・note の定期タスクの変更（一切触らない）。
- 1日に複数の漫画を作ること。複数選択。
- 週末・休場日の候補出し。
- 朝ブリーフィング側の変更（納品物の形は変えないので不要）。

**失敗とみなすもの（動いていても失敗）**
- ユーザーが締切までに選んだのに、別のネタで描かれる（理由の通知なしに）。
- 選択の有無にかかわらず、翌朝のメールに漫画が載らない日が増える。
- 候補出しや制作が、ほかの定期タスク（note・朝ブリーフィング）と時間・資源で干渉する。
- 候補に、確かめていない数字や投資助言に当たる表現が入る。
- 候補の題材・セリフ・下調べメモが公開リポジトリに入る。

## 3. 決まったこと（ユーザー判断）

| 項目 | 決定 |
|---|---|
| 候補を出す時刻 | 平日 14:00 ごろ |
| 選択の締切 | 20:00 |
| 制作の開始 | **20:05**（いまの 17:45 から移す）。納品と通知は **22:00 まで** |
| 候補の数 | 4件＋自由記述欄 |
| 注意喚起の週2回上限 | **ユーザーが選んだ場合は上限を超えても描く**（ユーザーの選択を優先）。自由記述で失敗談を頼まれた場合も同じ |
| 選択と自由記述 | 候補を1つ選び、さらに任意で「この候補で入れてほしいこと」を書ける。候補を選ばずに自由記述だけで頼むこともできる（note の「これも入れて」と同じ使い方） |
| 前提が引けで崩れたとき | **同じ題材のまま、引けの数字に合わせて切り口を変えて描く**（「あなたの選択（引けに合わせて調整）」と通知）。題材の中身そのもの（用語・仕組み）が成り立たないときだけ差し替える |
| 難易度☆の使い方 | 選ぶときの目安に加えて、台本と解説の深さの目安にも使う。manifest の履歴に残す |
| 候補出しのモデル | sonnet（調べ物が中心で、費用を抑えるため） |
| 制作のモデル | opus のまま（台本と絵の確認の質のため） |
| 作り方 | 案A：漫画専用のネタ選びページを新しく作る（§5） |

## 4. 全体の流れ（平日）

```
13:55  候補出しタスク（新しい定期タスク・sonnet）
        ├ 休場日なら何もしない
        ├ 材料を集める：朝・前場の JSON、ニュース（Web 検索）、note の今日の候補、前回までの漫画の履歴
        ├ 候補4件と、候補ごとの下調べメモを作る
        ├ ネタ選びページの保存領域に書き込む（days / notes）
        └ 通知「🐾 漫画のネタ候補が出ました（締切 20:00）」＋ページのリンク
〜20:00 ユーザーがページで1件を選ぶ、または自由記述で頼む（picks に保存される）
20:05  制作タスク（既存の定期タスクの時刻を変更・opus）
        ├ 選択を確かめる（picks）
        │   ├ 候補を選んでいる → その候補と下調べメモで描く
        │   ├ 自由記述がある → その内容で題材を立てて描く
        │   └ 選択なし → これまでどおり Claude が選ぶ（候補から選んでも、別の題材でもよい）
        ├ 以降は元の設計書どおり（台本 → 描画 → 確認 → 組版 → 納品）
        └ 22:00 までに通知
翌6:40 朝ブリーフィング（変更なし）
```

- 金曜の候補・選択は、月曜朝の漫画になる。祝日の前日も同じ（元の設計書の `next_business_day` どおり）。
- 13:55 はほかの定期タスク（11:47〜12:30 note 候補、15:35 引けデータ取得、16:15〜17:30 note 日次）と重ならない。
  20:05〜22:00 も重ならない（note の長文記事は 19:30 まで）。
- 13:55 の時点では大引けの数字がまだない。候補は前場（11:35 取得の JSON）とニュースを材料にし、
  数字の最終確認は 20:05 の制作で引けの値（15:35 取得の JSON・報道の大引け値）を使って行う。

## 5. 作り方の案（比較）

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **A. 漫画専用のネタ選びページ（採用）** | 「朝マンガ ネタ選び」を新しい Artifact として作る。候補出しが書き込み、ユーザーが選び、制作が読む | note と切り離せる（不具合・改修が互いに響かない）。note のページの作りを流用できる | 見るページが1つ増える（通知のリンクから開くので手間は同じ） |
| B. note のネタ選びページに漫画欄を足す | 同じページで両方を選ぶ | 見るページが1つ | note の仕組み（別ブランチで改修中）に手を入れる。締切が 16:15 と 20:00 で混在し分かりにくい |
| C. 「朝マンガ納品」ページに選択欄を足す | 上部で選び、下部で完成品を見る | 漫画が1ページで完結 | 納品ページは毎晩丸ごと作り直されるので、選択欄とぶつかりやすい。最も複雑 |

採用理由：note に触れずに済み、締切・不具合が漫画だけで閉じる（ユーザー判断で A）。

## 6. 各部の設計

### 6.1 ネタ選びページ「朝マンガ ネタ選び」

- 非公開の Artifact（固定 URL）。保存領域（データベース。Artifact の `db` 機能）を持つ。
  note のネタ選びページ（`docs/note-pipeline/picker.html`、ブランチ `claude/dazzling-goldberg-ceo0fc`）と同じ作りにする。
- ページのソースは `docs/manga/picker.html` に置く（公開してよい。候補の中身はページのソースではなく保存領域に入るため）。
- 保存領域の形（キー名の細部は作る人に任せる）:
  - `days/<作成日 YYYY-MM-DD>`：その日の候補。
    `{date, for_date, deadline: "20:00", created_at, candidates: [{id: "c1"〜"c4", title, kind, difficulty: 1|2|3, summary, hook, characters, caution_count_note}]}`
    - `kind`：`theme` / `term` / `stock` / `caution`（元の設計書 §4.1）
    - `summary`：あらすじ1〜2行。`hook`：解説に入れる予定の「へえ」と思う豆知識1行
    - `caution_count_note`：注意喚起の候補で、今週の上限（2回）に達している場合だけ「今週3回目」などと入れる
  - `notes/<作成日>`：候補ごとの下調べメモ（使う数字と出典、台本の骨子）。制作が使い回す。ページには出さない。
  - `picks/<作成日>`：ユーザーの選択。`{id: "c2" | null, request: "<この候補で入れてほしいこと>" | null, free: "<自由記述だけで頼む内容>" | null, picked_at}`
    - `id` と `request` は組で使う（`request` は `id` があるときだけ有効）。`free` は `id` がないときに使う。
    - ページでは「候補を選ぶ（＋任意で要望）」と「自由記述だけで頼む」のどちらか一方を保存する。両方を同時に保存させない。
- 画面（ユーザーが見るもの）:
  ```
  朝マンガ ネタ選び            11/27(金) 作成 → 11/30(月) 朝に掲載   締切 20:00
  ○ c1 ☆1 用語     PTSって何？夜の株価の読み方
       あらすじ1〜2行 / 豆知識：…
  ○ c2 ☆2 振り返り 日経とTOPIXの差がまた開いた日
  ○ c3 ☆2 話題     決算で急騰した電線株と「連れ高」
  ○ c4 ☆3 注意喚起 SNSで話題の小型株に飛びつく前に（今週3回目）
     この候補で入れてほしいこと（任意）[                         ]   ← 候補を選ぶと出る
  ○ 自由記述だけで頼む [                                  ]
  [ 保存 ]   いまの選択：c2 ＋ 要望「PTSの時間帯も入れて」（13:12 に保存）
  ```
  - 選んだ後も締切までは変更できる。締切を過ぎたら選択欄を閉じ、「締切済み」と出す。
  - 直近数日の候補と、そのうちどれを選んだかを下に小さく出す（任意。作る人の判断）。
- 難易度の基準（Claude の提案。候補出しの手順書に書く）:
  - ☆1：用語の基本（例：PTS とは、ストップ高とは）
  - ☆2：指標・値動きの読み方（例：日経平均と TOPIX の差、出来高の見方）
  - ☆3：需給・制度の応用（例：信用買い残、SQ、指数の入れ替え）

### 6.2 候補出しタスク（新規）

- 定期タスク「朝マンガ ネタ候補（平日13:55）」、cron `CRON_TZ=Asia/Tokyo 55 13 * * 1-5`、毎回新しいセッション、モデル sonnet、スマホ通知あり。
- 手順書は `docs/manga/candidates-task-prompt.md`。夕方制作と同じく、指示文からそれを読ませる。
- 手順:
  1. 東証の休場日なら、何もせず終了（通知なし）。
  2. 材料：`macro_result.json`・`macro_result_midday.json`・`screening_result_midday.json`、Web 検索、
     note の今日の候補（`https://claude.ai/artifact/9VFKNAzE2WiupWAPoj7bir` の `days/<今日>`。読めなければ飛ばす）、
     納品先の前回 manifest の `history`、ネタ選びページの直近の `days`（同じネタを繰り返さないため）。
  3. 候補4件を作る。種類を散らす（4件すべてが同じ kind にならない。目安は theme・term・stock から少なくとも各1件）。
     注意喚起は、今週の上限に達していても候補に出してよいが、`caution_count_note` で明示する。
  4. 候補の数字・豆知識は、出典を確かめたものだけ。確かめられないものは候補に入れない。投資助言に当たる表現は使わない。
  5. `days/<今日>` と `notes/<今日>` を保存する（ArtifactData）。
  6. 通知：`🐾 漫画のネタ候補が出ました（締切 20:00）：①<c1の題> ②… ③… ④…` とページのリンク。14:30 までに送る。
- GitHub への書き込みは不要（リポジトリは公開なので clone で読める）。

### 6.3 制作タスク（既存の変更）

- 定期タスク「朝マンガ 夕方制作」の時刻を **20:05** に変える（cron `CRON_TZ=Asia/Tokyo 5 20 * * 1-5`）。名前も時刻に合わせて変える。
- 手順書 `docs/manga/evening-task-prompt.md` を次のように変える:
  - **最初に選択を確かめる**：`picks/<今日>` を読む。
    - `id` がある → その候補（`days`）と下調べメモ（`notes`）を題材にする。題材決めのフェーズは飛ばす。
      `request` があれば台本と解説に取り入れる（投資助言・未確認の数字など、ルールに反する部分は取り入れず、通知に一言書く）。
      注意喚起の週2回上限は適用しない（ユーザーの選択を優先）。
    - `free` がある（`id` なし）→ その内容から題材を立てる（kind・難易度は Claude が決める）。
      失敗談を頼まれた場合は注意喚起の回として描き、週2回上限は適用しない。
    - どちらもない → これまでどおり Claude が選ぶ。候補4件の中から選んでもよい。
  - **前提が引けで崩れたとき**（例：「日経と TOPIX の差が開いた」を選んだが、引けでは縮んだ）：同じ題材のまま、
    引けの数字に合わせて切り口を変える（「前場は開いたが、引けでは縮んだ。なぜか」）。これは「あなたの選択」として扱い、
    通知に「（引けに合わせて調整）」と書く。下調べメモの台本の骨子は、数字と切り口を直してよい。
    題材の中身そのもの（用語・仕組み・出来事）が成り立たないときだけ、差し替えにする。
  - **難易度の使い方**：☆1 は用語をかみくだいて説明し、数字は1〜2個まで。☆2 はその日の数字と読み方。
    ☆3 は数字や仕組み（需給・制度）まで踏み込む。解説の字数（350〜550字）は変えない。おまかせの日も、Claude が難易度を付ける。
  - **選ばれたネタが描けない場合**（数字の裏付けが取れない、投資助言にしかならない、描き直し上限を使っても重い問題が残る、など）は、
    Claude の選んだネタに切り替えて描き、通知に「選択ネタは<理由>のため差し替え」と書く。
    描き直し上限で残った場合は、元の設計書どおりその日を見送る（差し替えて描き直す時間はない）。
  - 締切を移す：題材 20:15 → 台本 20:30 → 描画の待ちは 21:35 で打ち切り → 納品 21:50 → 通知 **22:00**。
  - 通知の成功文に、選択の有無を入れる：`🐾 明日の漫画ができました：<title>（あなたの選択 / おまかせ / 差し替え）`。
    2行目の描き直しの記録（元の手順書どおり）はそのまま。
  - manifest の `history` に、選択の有無（`picked: "user" | "free" | "auto" | "replaced"`）と難易度（`difficulty: 1|2|3`）を足す（傾向を見るため）。
    `user` は候補を選んだ日（引けに合わせて調整した日も含む）、`replaced` は選択ネタを差し替えた日。

## 7. ユーザー作業

- 新しい候補出しタスクには、リポジトリを付けなくてよい（GitHub への書き込みがないため）。
- 制作タスクの時刻変更は Claude が行う（Claude が作った定期タスクなので変更できる）。リポジトリの付与はそのまま。
- 新しい定期タスクの作成と、制作タスクの時刻変更は、ユーザーの承認を得てから行う。

## 8. 作る人に任せること

- `picker.html` の見た目（note のネタ選びページに合わせる。Meiryo UI を先頭に）。
- 保存領域のキー名の細部、直近の候補の表示の有無。
- 候補出しの材料の集め方の細部（何件ニュースを見るか、など）。
- テストの範囲（候補 JSON の検証、選択の読み分けの関数など、Python に切り出せる部分はテストを付ける）。
- 候補出しが失敗した日の通知文、締切後に保存しようとしたときのページの振る舞い。

## 9. Claude が決めたこと（ユーザーの確認用）

- 難易度の基準（☆1 用語の基本、☆2 指標・値動きの読み方、☆3 需給・制度の応用）（§6.1）
- 候補は種類を散らし、注意喚起は上限に達していても「今週3回目」と明示して出してよい（§6.2）
- 候補出しは 13:55 開始、14:30 までに通知（§6.2）
- 制作の締切の割り振り（題材 20:15 → 台本 20:30 → 描画の待ち 21:35 → 納品 21:50 → 通知 22:00）（§6.3）
- 差し替えた日は manifest の履歴に `replaced` と残す（§6.3）
